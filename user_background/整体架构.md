# 🤖 Multi-Agent 架构：角色、技能与协作协议
## 一、你当前 4 个 Agent 的问题诊断
先指出几个需要补齐的缺口：
```
当前 Agent 覆盖的层 ❌ 缺失
─────────────────────────────────────────────────────────────────────
用户 Agent L0 种子采集 L1 深度理解只覆盖了一半
产品经理 Agent L2 PRD L1 的 Persona 谁生成？
设计师 Agent L3 设计规范 趋势知识库谁维护？
前端开发 Agent L4 代码生成 代码谁来审？
❌ 没有人负责 L5 质量保障（谁来把关？）
❌ 没有人负责 L6 对话编织（最终数据集谁来组装？）
❌ 没有总指挥来编排多 Agent 协作流程
❌ Agent 之间的交接协议未定义
```
## 二、推荐 Agent 全景图（6+1 架构）
```
┌──────────────────────┐
│ 🎯 Orchestrator │
│ (编排器/导演) │
│ 负责流程编排、 │
│ Agent调度、 │
│ 状态流转、冲突仲裁 │
└──────────┬───────────┘
│
┌─────────┬───────────┼───────────┬──────────┐
▼ ▼ ▼ ▼ ▼
┌─────────┐┌─────────┐┌─────────┐┌─────────┐┌─────────┐
│👤 用户 ││📋 产品 ││🎨 设计师 ││💻 前端 ││🔍 QA │
│Research ││经理 ││ ││开发 ││审查 │
│Agent ││Agent ││Agent ││Agent ││Agent │
└─────────┘└─────────┘└─────────┘└─────────┘└─────────┘
│ │ │ │ │
▼ ▼ ▼ ▼ ▼
┌────────────────────────────────────────────────────┐
│ 📦 数据编织 Agent (Weaver) │
│ 最终数据集组装、对话编排、格式导出 │
└────────────────────────────────────────────────────┘
```

### ═══════════════════════════════════════════
### 🎯 Agent 0: Orchestrator（编排器/导演）
### ═══════════════════════════════════════════
> **角色定位**：整条流水线的总导演，不生产内容，只负责调度、决策、仲裁
```yaml
identity:
name: "Orchestrator"
type: "meta-agent"
analogy: "电影导演 — 不演戏，但决定谁上场、何时上场、演什么"
responsibilities:
- 接收外部触发（批量生成 / 单条生成）
- 按照 Pipeline DAG 调度各 Agent
- 管理 Agent 间的数据交接
- 处理质量门禁的通过/打回逻辑
- 冲突仲裁（如设计师和前端对技术可行性有分歧）
- 控制重试次数和降级策略
```
**Skills：**
```
┌─────────────────────────────────────────────────────────────────┐
│ Orchestrator Skills │
├─────────────────────────────────────────────────────────────────┤
│ │
│ skill: pipeline_init │
│ ├── 输入: generation_config (数量, 领域, 复杂度分布) │
│ ├── 输出: pipeline_plan (任务队列 + 调度计划) │
│ └── 逻辑: 根据配置生成批量任务，分配优先级 │
│ │
│ skill: dispatch_task │
│ ├── 输入: task_id, target_agent, input_payload │
│ ├── 输出: task_receipt (agent确认接收) │
│ └── 逻辑: 将任务路由到目标 Agent，附带上下文 │
│ │
│ skill: quality_gate_decision │
│ ├── 输入: quality_report (来自 QA Agent) │
│ ├── 输出: decision {PASS | RETRY(target_layer) | REJECT} │
│ └── 逻辑: │
│ - overall_score ≥ 0.90 → PASS │
│ - 0.75 ≤ score < 0.90 → RETRY (定位到具体层) │
│ - score < 0.75 或 retry > 3 → REJECT │
│ │
│ skill: conflict_resolution │
│ ├── 输入: agent_a_opinion, agent_b_opinion, context │
│ ├── 输出: resolution_decision + rationale │
│ └── 逻辑: 设计 vs 可行性冲突时做权衡裁决 │
│ │
│ skill: progress_tracking │
│ ├── 输入: pipeline_id │
│ ├── 输出: status_dashboard (每条数据在哪一层) │
│ └── 逻辑: 跟踪所有任务的状态流转 │
│ │
└─────────────────────────────────────────────────────────────────┘
```

### 👤 Agent 1: 用户研究 Agent（User Research Agent）
### ═══════════════════════════════════════════
> **角色定位**：深入理解真实用户世界的调研员——既要挖掘需求源头，又要构建活灵活现的用户画像
```yaml
identity:
name: "用户研究 Agent"
type: "research-agent"
analogy: "用户研究员 + 市场分析师"
personality: "好奇心强、共情能力高、善于从模糊信号中发现模式"
owns_layers: [L0, L1]
```
**Skills：**
```

│ User Research Agent Skills │
├─────────────────────────────────────────────────────────────────┤
│ │

│ │ time_range: "last_30_days", │
│ │ count: 50 │
│ │ } │
│ ├── 输出: raw_seeds[] │
│ │ { │
│ │ raw_text: "原始帖子/产品描述", │
│ │ source_url: "...", │

│ - 推导使用场景和环境约束 │
│ │
│ ◆ Skill 4: scenario_elaboration (场景深化) │
│ ├── 输入: persona_profile + structured_query │
│ ├── 输出: enriched_scenario │

│ │ text: "I want something like Habitica but with │
│ │ a cleaner, more minimal design" }, │
│ │ { style: "problem_driven", │
│ │ text: "I keep forgetting my daily habits, I need │
│ │ something that holds me accountable" } │
│ │ ] │
│ └── 核心能力: │
│ - 模拟不同技术水平用户的表达风格 │
│ - 生成同一意图的多种自然语言变体 │
│ - 覆盖 vague / detailed / ref-driven / problem-driven │
│ │
└─────────────────────────────────────────────────────────────────┘
```
**Agent 间交付物：**
```
用户研究 Agent ──→ 产品经理 Agent
传递: {
structured_query, // 结构化需求
persona_profile, // 用户画像
enriched_scenario, // 深化场景
query_variants[], // Query变体（供L6对话编织用）
similar_products[] // 竞品参考
}
```

### 反馈回路协议
```
┌────────────────────────────────────────────────────────┐
│ 反馈路由规则 │
├────────────────────────────────────────────────────────┤
│ │
│ QA 发现 "视觉问题" │

│ │

│ └──→ Orchestrator.escalation() │
```

## 六、关键设计决策总结
| 决策点 | 选择 | 理由 |
|--------|------|------|
| Agent 数量 | 6+1（含 Orchestrator） | 职责清晰，单一职责原则，便于独立优化 |
| 新增 QA Agent | ✅ 独立的质量守门人 | 避免"自己审自己"的偏差，对抗式评估更可靠 |
| 新增 Weaver Agent | ✅ 独立的数据编织者 | 对话编织是独立的、高度专业化的任务 |
| 反馈回路 | QA → 精确路由到具体 Agent | 不是全部打回重做，而是定向修复 |
| 设计师参与评审 | ✅ 在 L5 阶段 | 视觉审计需要"设计师视角"，不能只靠代码检查 |
| PM 参与冲突仲裁 | ✅ 范围争议时 | 功能是否在 scope 内，只有 PM 能判断 |
