# PerfScope PRD

## 1. 文档信息
- 产品名称：PerfScope
- 产品类型：开发者工具 / 系统性能分析
- 版本范围：MVP + 后续迭代建议
- 文档目标：为下游设计师、前端与工程团队提供可执行的产品规格，聚焦“系统性能瓶颈”诊断，而非概念展示

## 2. 产品概述
PerfScope 是一个面向前端工程师、全栈工程师和性能优化负责人的性能分析工作台，用于在高密度数据环境下快速定位系统性能瓶颈。产品支持导入性能追踪数据，提供总览指标、时间线分析、瓶颈列表、明细表格和自然语言查询入口，帮助用户从“发现异常”到“定位原因”再到“形成优化假设”。

本产品不是通用 BI 仪表盘，也不是纯展示型官网。核心价值是提升工程诊断效率，降低从海量性能事件中找到关键问题的时间成本。

## 3. 背景与问题定义
用户的真实需求不是“需要很多炫技 UI 能力”，而是：
1. 数据量很大时，现有工具卡顿，难以交互查看
2. 性能数据复杂，问题定位链路长
3. 不同维度数据分散，缺少统一工作台
4. 新手或非性能专家难以快速提问和获得分析方向
5. 开发者长时间使用，需要暗黑模式、高信息密度与稳定交互

输入中包含 WebGL、动态 SVG、语音控制、新拟态等要求，但并非都应进入 P0。MVP 应优先服务“分析效率”和“可用性”，而不是为技术特性本身服务。

## 4. 产品目标
### 4.1 业务目标
1. 将用户从导入数据到识别可疑瓶颈的时间压缩到 5 分钟内
2. 让用户在单一工作台内完成总览、筛选、钻取、查询和导出
3. 支持高数据量情况下仍保持流畅交互，避免工具本身成为性能瓶颈

### 4.2 用户目标
1. 快速知道“问题在哪里”
2. 能按时间段、模块、线程、事件类型筛选
3. 能看到关键瓶颈的排序和证据
4. 能通过自然语言快速发问，而不是必须理解底层数据结构
5. 能在深色、高密度界面中长时间稳定使用

### 4.3 非目标
1. 不在 MVP 中做完整语音控制工作流
2. 不做过度装饰性的 3D 视觉演示
3. 不做强品牌展示页式 UI
4. 不在首版中覆盖所有性能数据标准和所有运行环境
5. 不做自动修复代码，仅提供分析与建议线索

## 5. 目标用户
### 5.1 核心用户
- 前端工程师：分析页面卡顿、长任务、渲染阻塞、交互延迟
- 全栈/平台工程师：分析接口耗时、任务堆积、系统资源争用
- 性能专项负责人：查看关键瓶颈、对比优化前后结果

### 5.2 次级用户
- QA / 测试工程师：复现并确认性能问题
- 技术经理：查看关键性能问题概况，但不是首要交互对象

## 6. 核心使用场景
1. 用户导入一次性能追踪数据，系统自动生成总览与异常摘要
2. 用户在时间线中缩放到异常区间，联动查看相关模块与事件
3. 用户通过瓶颈列表快速看到高影响问题，例如长任务、渲染阻塞、慢接口、频繁重排
4. 用户在表格中按耗时、调用次数、影响范围排序和过滤
5. 用户输入自然语言问题，例如“为什么首屏交互延迟高？”并获得结构化回答与关联视图跳转
6. 用户对比一次优化前后的数据差异，验证是否有效

## 7. MVP 范围收敛
### 7.1 P0 必做
1. 性能数据导入
2. 总览页：关键指标卡 + 趋势图 + 异常摘要
3. 时间线 / Trace Explorer：支持大数据量浏览、缩放、筛选
4. 瓶颈列表：按影响度排序并可跳转到对应时间区间
5. 高性能暗黑数据表格：排序、筛选、列配置、固定表头、虚拟滚动
6. 自然语言查询入口：文本输入，不做语音
7. 基础洞察建议：规则驱动的“可能原因”
8. 结果导出：导出当前筛选视图或问题摘要

### 7.2 P1 应做
1. WebGL 或 Canvas 渲染加速的超大规模时间线
2. 对比分析视图：优化前后数据并排对比
3. 更丰富的图表联动与微交互
4. 保存查询视图 / 保存筛选器
5. URL 状态分享

### 7.3 P2 可选
1. 语音控制
2. 高度拟物或新拟态风格实验
3. AI 自动生成更完整优化方案
4. 多人协作批注

## 8. 需求取舍原则
### 8.1 WebGL
- 保留为“性能手段”，不是视觉卖点
- 若常规虚拟化 + Canvas 已满足性能目标，则 WebGL 可延后到 P1

### 8.2 动态 SVG 与微交互
- 图表应有必要的交互反馈，但动画不应影响分析效率
- 动画默认短、克制、可关闭

### 8.3 语音控制
- 不是核心诊断路径
- 首版用自然语言文本查询替代，避免环境噪音、隐私、识别准确率与工程复杂度风险

### 8.4 新拟态风格
- 与高密度 DevTools、暗黑模式、可读性和可访问性存在冲突
- 首版采用“现代深色工具型风格”，可保留轻微柔和层次，不使用重阴影软 UI 作为主视觉语言

## 9. 功能规格
## 9.1 数据导入
### 目标
让用户能快速加载一份可分析的数据集。

### 功能要求
- 支持本地文件上传
- 支持 JSON / Trace 类结构化数据
- 导入后进行基础解析与字段校验
- 解析失败时给出明确错误原因和示例格式
- 对大文件提供进度反馈与非阻塞处理

### 成功标准
- 中等规模数据文件可成功导入并进入分析页
- 导入失败可被定位到字段或格式问题

## 9.2 总览页
### 目标
用户进入产品后 30 秒内知道是否存在明显瓶颈。

### 功能要求
- 展示关键指标：总耗时、长任务数、渲染阻塞、慢请求数、错误数、峰值区间
- 展示趋势图 / 分布图
- 展示“异常摘要卡片”
- 提供快速过滤入口
- 点击指标可联动跳转到 Trace Explorer 或表格

### 成功标准
- 用户能从总览直接进入至少一个可疑瓶颈详情路径

## 9.3 Trace Explorer
### 目标
支持用户查看高密度时间序列事件并钻取具体问题。

### 功能要求
- 横向时间轴
- 支持缩放、拖拽、框选区间
- 按线程 / 模块 / 事件类型分层展示
- hover 查看摘要，click 查看详情侧栏
- 与筛选器和表格联动
- 空间不足时采用聚合显示
- 大数据量下保持平滑操作

### 成功标准
- 主要交互不因数据量明显卡顿
- 用户能定位到问题区间并查看相关事件详情

## 9.4 瓶颈列表
### 目标
将复杂数据转化为可排序的问题清单。

### 功能要求
- 按影响度、耗时、频次、范围排序
- 标注问题类型，例如长任务、主线程阻塞、慢接口、频繁重排
- 支持一键跳转关联时间段
- 支持状态标签：高优先级、中优先级、建议关注
- 可导出当前列表

### 成功标准
- 用户不需要先读完整时间线，也能知道从哪里开始排查

## 9.5 数据表格
### 目标
提供工程化明细分析能力。

### 功能要求
- 虚拟滚动
- 固定表头与关键列
- 列排序、列显隐、列宽调整
- 多条件筛选
- 行展开查看详情
- 与其他视图联动
- 支持复制值、导出 CSV

### 成功标准
- 10k+ 行数据仍可用
- 表格是诊断主工作区之一，而非补充信息面板

## 9.6 自然语言查询
### 目标
降低理解门槛，提升定位效率。

### 功能要求
- 提供文本输入框
- 支持问题示例提示
- 输出结构化结果：结论、证据、关联视图入口、推荐下一步
- 支持常见查询，如“哪个模块最慢”“为什么交互延迟高”“最近的长任务集中在哪”
- 查询结果可以反向驱动页面筛选

### 成功标准
- 首次用户可通过示例问题完成一次有效查询
- 查询不是聊天玩具，而是分析导航入口

## 9.7 导出与分享
### 目标
让用户能沉淀问题与结果。

### 功能要求
- 导出当前筛选结果
- 导出瓶颈摘要
- P1 支持带状态的分享链接

## 11. 交互与视觉原则
### 11.1 总体原则
- 高信息密度，但保持层级清晰
- 默认暗黑模式
- 优先可扫描性，不追求大面积留白
- 交互反馈短促明确
- 图表与表格联动优先于装饰性动画

### 11.2 视觉方向
- 深色底 + 中高对比文本
- 用有限强调色区分问题等级和数据类型
- 卡片、面板、表格统一组件体系
- 使用轻层次阴影与边框，不采用重度新拟态软 UI
- 保持专业、工具化、理性气质

### 11.3 布局建议
- 顶部：全局筛选、时间范围、搜索/查询入口、导入与导出
- 左侧：主导航
- 中区：主分析区
- 右侧：上下文详情侧栏，可折叠
- 表格与时间线支持上下或左右分栏切换

## 12. 性能与技术约束
### 12.1 前端性能目标
- 初次可交互时间应尽量短
- 主分析交互保持流畅，缩放/筛选/滚动不出现明显阻塞
- 大数据场景采用虚拟化、分层渲染、按需计算、懒加载

### 12.2 渲染建议
- 表格优先虚拟列表
- 图表避免 DOM 过载
- 时间线优先 Canvas / 混合渲染方案；数据量继续增长时再引入 WebGL
- 动画降级策略必须存在

### 12.3 可访问性
- 支持键盘导航的核心路径
- 保证深色模式下文字与图表颜色对比
- 状态颜色不能是唯一编码方式，需配合标签/图标/文本

## 13. 数据与分析模型建议
### 13.1 核心实体
- Trace Session
- Event
- Thread / Lane
- Module / Service
- Bottleneck Insight
- Query Result
- Saved View（P1）

### 13.2 基础分析维度
- 时间区间
- 事件类型
- 模块 / 服务
- 调用链 / 线程
- 耗时
- 频次
- 影响范围
- 错误/警告状态

## 14. 成功指标
### 14.1 产品指标
- 首次导入完成率
- 首次查询使用率
- 问题定位完成率
- 从导入到首次点击瓶颈详情的平均时长
- 导出摘要使用率

### 14.2 体验指标
- 大数据场景下关键交互掉帧率
- 查询结果被点击跳转的比例
- 表格与时间线联动成功率
- 导入失败率及失败原因分布

## 15. 验收标准
1. 用户可完成“导入数据 -> 看总览 -> 定位瓶颈 -> 查看明细 -> 导出结果”的主流程
2. 高密度界面在暗黑模式下可读性稳定
3. 表格、图表、时间线在交互上相互联动
4. 自然语言查询可返回结构化分析结果而非泛泛回答
5. 首版没有把语音、新拟态等非核心特性强行做成 P0

## 16. 风险说明
1. “新拟态”与“高密度 DevTools”在可读性、层级清晰度、专业感上存在明显冲突，已降级为局部风格参考，不作为主视觉方案
2. “语音控制”对开发者真实使用场景价值有限，且涉及噪音、权限、准确率与隐私问题，已从 P0 移除
3. “WebGL 渲染引擎”实现成本较高，只有在 Canvas/虚拟化方案无法满足性能目标时才作为必要方案推进
4. 自然语言查询若接入模型能力，需要定义可解释性边界，避免输出不可靠结论
5. 数据来源格式若不统一，导入和标准化成本会明显上升

## 17. 待确认问题
1. MVP 首版需要支持哪些具体性能数据格式
2. 自然语言查询是纯规则驱动，还是接入模型能力生成解释
3. 是否需要对比分析作为首版的一部分，还是延后到 P1
4. 产品主要聚焦前端性能，还是要兼容更广义系统性能数据
5. 是否存在团队级分享或协作需求
