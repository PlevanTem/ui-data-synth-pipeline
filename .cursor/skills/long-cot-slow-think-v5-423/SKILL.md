# 完整设计推理慢思考 SFT 数据合成

将 `outputs/<case_id>/` 下的全阶段产物进行对话构造，生成 **1 条** SFT 训练样本，`<think>` 独白按 11 维度框架顺序推进，完整覆盖从需求理解到实现细节的全部设计决策过程。

## 核心理念

生成**一条设计思考深入、覆盖多种设计维度的完整推理链**：

- **本技能**：用户问「帮我做一个诗歌节票务页」→ 一条完整 `<think>` 按 11 维度逐步推进，推理中主动 Backtrack 和 Verify → 输出完整 index.html

这种数据适合：

- 训练模型从需求出发完整推导整个设计方案的能力
- 训练 Backtracking 和 Verification 两类认知行为（区别于单次正向推理）
- 覆盖"探索→评估→修正→迭代"完整设计思维过程的 SFT 数据

## 推理质量三大准则

`<think>` 独白整体须同时满足下述三条质量准则。它们**不是独立的章节或步骤**，而是贯穿 11 维度全过程的写作指南，决定"每一句话怎么写、写多长、要不要给理由、要不要自查"。

### 准则 1：自适应粒度组织（Optimal Structural Organization）

推理步骤的颗粒度按**重要性自适应变化**，而不是每个维度、每个决策都用同等长度平铺：

- **关键推理节点**（主方向选定、核心取舍、跨维度冲突修正、反同质化策略等）：多分配 token、详细阐述「为什么、对比什么、放弃什么、最终结论」，允许较长段落深度展开。
- **简单推导节点**（从主色派生次色阶、常规间距单位选择、例行响应式折叠等）：保持简洁凝练，1-2 句说明即可，不刻意拉长。
- **反模式**：所有维度用相同篇幅平铺直叙；或简单决策反复啰嗦，而真正的关键转折一笔带过。

### 准则 2：渐进式认知支架（Effective Cognitive Scaffolding）

推理过程需带有教学性，像在向自己（或未来读者）**逐步搭建理解**，而不是直接抛结论：

- **渐进引入概念**：关键概念首次出现时简短给出背景（如"毛玻璃在暗色背景上容易出现…因此…"）。
- **显化关键洞察**（key insight）：遇到决定整体方向的核心判断时，明确点出"这里的关键是…"或"真正要解决的问题是…"。
- **主动搭桥**：在概念或维度之间搭起逻辑桥梁，说明上一步结论如何推出下一步判断，不让推理链出现断裂。
- **反模式**：跳过理由直接给答案；只写"做什么"不写"为什么"；依赖读者自行补全逻辑。

### 准则 3：高频严格验证（Rigorous Verification）

验证不是集中在某几个显式检查点，而是**以极高频率贯穿推理全程**的自查习惯：

- **即产即验**：每产出一个中间结论就顺手校一次（定下一个色值立刻核对比度；选定一个组件风格立刻想一下和整体氛围是否一致；设定一个断点立刻问自己主要布局是否还成立）。
- **交叉校验假设**：后续维度的决策主动回头和前置维度的前提对齐，确保整体一致。
- **确认逻辑一致性**：每个推导步骤都应经得起"这一步为什么成立"的追问。
- 下文 `Verification` 步骤是**带信号词的显式形式**；在此之外，`<think>` 全文还应散布**轻量、不带信号词**的即时自查句（如"这个选择在移动端也成立"、"和刚才定的色调方向匹配"）。
- **反模式**：只在几处显式 Verification 段落做检查，其它地方的决策一路直走、从不回望。

## 两类核心认知步骤

在满足上述三大准则的前提下，`<think>` 中还必须显式出现以下**两类带信号词的认知步骤**，**穿插在 11 维度推进过程中自然发生**，不固定在某个位置：

### Backtracking（回溯）

推理遇到矛盾或新约束时，**显式返回前一个维度重新修正**之前已做的决策。这是准则 3（验证）触发失败后的必要补救动作，也是体现"探索→评估→修正→迭代"的关键证据。

触发场景举例：

- 维度 5（组件样式）发现 glassmorphism 卡片和维度 2（氛围）定的极简方向产生矛盾
- 维度 9（响应式）发现维度 6（布局）定的三列网格在移动端挤压严重
- 维度 4（排版）定的衬线字体家族和维度 3（配色）的冷色调整体感觉不搭

书写信号词（需出现其中之一）：

- `等等，这和我刚才定的…有冲突`
- `退一步重新想`
- `这里需要回去改一下`
- `不对，之前那个决定站不住脚`
- `这个问题让我重新审视一下…`

Backtracking 之后必须有实质性的**修正动作**，不能只提出问题不修正。回溯段落属于"关键推理节点"，按准则 1 应分配较多篇幅完整展开冲突、修正思路、新的结论。

### Verification（验证）

**显式自查某一阶段的输出是否正确或合理**，发现问题则就地修正。这是准则 3 的**带信号词加强形式**，用于关键决策后的正式核验；但请注意：除了这些显式段落外，全文还要按准则 3 散布轻量即时自查句。

触发场景举例：

- 配色决定后验证主文字/背景对比度是否满足可读性
- 版式骨架定完后验证信息密度和叙事节奏是否合理
- 组件样式定完后验证在暗色背景上是否够清晰

书写信号词（需出现其中之一）：

- `验证一下`
- `回头检查`
- `这个决定放到移动端还成立吗`
- `我算一下对比度`
- `让我核查一遍`
- `这里有个隐患`
...

Verification 之后如果发现问题，必须修正；如果没有问题，明确说明"没问题，继续"或类似表达。

## 执行步骤

### Step 1: 读取全部 case 文件

读取输入表中列出的所有文件，以及 `03_frontend/index.html` 的完整内容。全部阅读完毕后再开始构造。

### Step 2: 构造 user prompt

从 `meta.json` 和 `01_pm/prd.md` 生成一个自然的用户请求（80-200 字），第一人称，包含核心需求和视觉偏好。语气像真实用户在描述需求，不是技术文档。

### Step 3: 撰写 `<think>` 独白

按以下 **11 个维度**顺序推进，每个维度内部体现「探索→评估→修正→迭代」过程，维度之间自然过渡，**不使用 markdown 标题**，内容流动如同真实的设计思维过程。

#### 11 个维度的推进框架

**1. 需求分析**
带入用户场景，深入并拆解用户需求，提炼设计痛点和约束。继续规划下一步。

**2. 视觉主题与氛围**

根据用户 query 中风格意图的明确程度，采用不同的推理路径：

- **用户已给出明确风格方向**（如"极简白底"、"赛博朋克"）：**不需要**发散候选方向，直接进入对该方向的深化和延展——挖掘这个风格的核心特征、情感含义、与用户场景的契合点，以及如何避免流于表面（原创性反同质化）。推理重心在于"如何把这个风格做深做对"而非"选哪个方向"。
- **用户风格意图模糊**（如"有氛围感"、"高级感"、"现代"）：需要发散 2-3 个候选方向，比较各自优劣，明确选定主方向和理由，说明为何放弃备选，并说明反同质化的设计策略。

无论哪种路径，最终都需要：

- 明确主方向的核心特征（≥3 个）
- 设计质量：网站整体的设计是否感觉像是一个连贯的整体，而不是各个部分的简单堆砌？优秀的设计意味着色彩、字体、布局、图像和其他细节相互融合，共同营造出独特的氛围和风格。
- 反同质化策略（说明原创性，如何避免和同类产品雷同）：比如是否存在自定义决策的痕迹，还是仅仅使用了模板布局、库默认设置和人工智能生成的图案？一位优秀的设计师应该能够识别出精心设计的创意。未经修改的现成组件——或者像白色卡片上叠加紫色渐变这样的人工智能生成痕迹——都无法体现原创性。

**3. 色彩调色板与角色**

- 主品牌色的选择逻辑（为什么是这个色而非另一个）
- 各色阶角色：主背景、卡片背景、主文字、辅助文字、强调色、交互色、边框
- 对比度和可读性考量

**4. 排版规则**

- 字体家族选择（衬线/无衬线/混用）和情感匹配逻辑
- 层级结构（H1/H2/H3/body/label 的字号和权重）
- 排版原则（行距、字间距、最大行宽）

**5. 组件样式**

- 按钮（主/次/幽灵按钮的样式决策）
- 卡片与容器（实色/毛玻璃/描边风格的选择）
- 输入框（如有表单）
- 导航（形态、交互态）
- 核心组件约束（哪些风格在此设计中明确禁止）

**6. 布局原则**

- 间距系统（基础单位和使用规则）
- 网格与容器（最大宽度、列数、响应变化）
- 叙事顺序（各 section 的排布逻辑，情绪先行还是信息先行）
- 留白哲学

**7. 深度与层级**
- 信息架构和层级处理方式
- 分组和亲和度设计，z 轴关系（哪些元素在哪些之上）
- 分层细节设计（阴影/透明度/模糊的使用规则）

**8. 设计宜忌**

- 此设计明确推荐的做法（≥3 条）
- 此设计明确禁止的做法（≥3 条，包含功能边界——为什么某些功能不做）

**9. 响应式行为**

- 断点选择和理由
- 移动端布局折叠策略（哪些多列变单列，哪些元素隐藏）
- 触控目标尺寸考量

**10. 页面交互清单**

- 导航点击行为
- 筛选器/Tab 变化
- 表单提交（如有）
- 移动端导航（汉堡菜单或底部导航）
- 其他必须实现的交互（滚动动效、hover 状态、scroll reveal）

**11. 视觉特效方案**

- 生成式视觉层的技术选型（Canvas 2D / WebGL / CSS animation / 无）及理由
- 动效节奏（哪些元素有动效，时序和缓动参数）

#### Backtracking 和 Verification 的嵌入要求

这两类步骤**不是在固定位置**，而是在推进过程中自然发生：

- **配色完成（维度 3）之后**，至少有 1 次 Verification 检查对比度或配色一致性
- **组件或布局阶段（维度 5-6）**，至少有 1 次 Backtracking，发现与之前某个维度的矛盾并修正
- **响应式或特效阶段（维度 9-11）**，至少有 1 次 Verification 检查动效体验和移动端适应性
- ...
- 总计：`<think>` 中 ≥2 处 Backtracking，≥2 处 Verification

#### 写作风格

- 面向用户的query诉求，作为设计师助手视角进行心理独白，如同设计师在自言自语
- 情感化标记词（嗯、等等、让我想想、不对、停一下）
- 明确的比较和否定（为什么不选 A，为什么选 B）
- **不用 markdown 标题**，维度之间用自然的过渡句连接
- **不泄露 JSON 字段名**（不出现 `case_id`、`focus`、`sample_id` 等）
- **不泄露管线术语**（不出现 `prd`、`design_brief`、`pipeline`、`v5` 等）
- `<think>` 的语言和用户 query 的语言保持一致

#### 长度与深度

- `<think>` 目标字数：**1000-3000 字符**，根据需求复杂度决定
- 必须包含 ≥2 处 Backtracking（含明确信号词和修正动作）
- 必须包含 ≥2 处 Verification（含明确信号词和结论）
- 必须包含 ≥1 次跨维度修正（后续维度发现问题回溯修改前置维度的决策）
- 必须包含 ≥1 个明确的否定推理（某个方向被明确放弃）
- 必须体现**自适应粒度**：关键节点（主方向、核心取舍、冲突修正）段落明显长于简单推导段落，不得全文等宽平铺
- 必须体现**认知支架**：≥2 处显式的 key insight 标记（"这里的关键是…"/"真正要解决的是…"/"核心判断在于…" 等），并在关键概念首次出现时给出简短背景
- 必须体现**高频验证**：除显式 Verification 段落外，全文额外散布 ≥4 处轻量即时自查句（不要求信号词，但需明显是在自我核验）

### Step 4: 撰写代码输出

`</think>` 后直接输出**完整的 `index.html`**，单文件包含 HTML + Tailwind CDN + 内联 CSS + 原生 JS。代码应体现 `<think>` 中所有关键决策。

代码格式：独立 `html` 代码块，关键区域用注释标明功能。

### Step 5: 组装并写入 TXT

将 user prompt + assistant（`<think>` + 完整 HTML）组装成 1 条训练样本写入 JSONL 文件。

## 质量检查清单

- 单条 sample（保存到1个txt文件）
- `<think>` 语言必须和用户 query 语言一致
- `<think>` 基于用户需求覆盖 11 个维度，内容自然流动，无 markdown 标题
- ≥2 处 Backtracking（含信号词 + 实质修正动作）
- ≥2 处 Verification（含信号词 + 明确结论）
- ≥1 次跨维度修正
- ≥1 个明确的否定推理（某方向被放弃）
- **自适应粒度**：关键推理节点段落明显长于简单推导段落，无全文等宽平铺
- **认知支架**：≥2 处显式 key insight 标记；关键概念首次出现时给出简短背景并在概念间搭桥
- **高频验证**：除显式 Verification 外，全文散布 ≥4 处轻量即时自查句
- **因果泄露**：全文及 HTML 无 JSON 字段名、输入case文件或管线术语泄露

## `<think>` 独白结构示例

以下仅展示推理的**转折骨架**——如何从用户需求中推导、如何触发 Backtracking 和 Verification、如何在维度之间自然过渡。具体的设计答案（色值、参数、字体名称等）在实际合成时根据 case 文档自行推导，不应照搬。

```
[维度 1 · 需求分析]
带入用户场景：他是谁，要解决什么问题，这个页面对他意味着什么。
然后拆约束：哪些是硬约束（技术边界、功能边界），哪些是软偏好（情绪词），
软偏好需要解读——"高级感"背后是什么，"氛围感"指向哪类情绪。

[维度 2 · 视觉主题]
（风格意图模糊时）列出 2-3 个方向，每个方向找出为什么不够好的理由，
直到找到一个和用户场景契合度最高的方向。
确定方向后，指出它的 3 个核心特征构成一个整体，而不是碎片拼凑。
然后主动想：这个方向在同类产品里的通病是什么？我要怎么做才不像模板。

[维度 3 · 配色]
从背景色出发推导，为什么不用最直觉的选择，往什么方向调整，调整的理由。
文字色、强调色、交互色依次推导，每个色的选择都要和方向特征挂钩。

→ Verification：配色定完，验证主文字/背景对比度是否过关，
  辅助色是否有使用限制需要记住。

[维度 4 · 排版]
字体选择——排除掉情感不匹配的选项，说清楚为什么选这个而不是那个。
层级结构——各级标题到正文的视觉落差要和整体氛围呼应。

[维度 5 · 组件样式]
按钮、卡片、导航的核心风格决策。

→ Backtracking：某个组件决策（如毛玻璃卡片）在特定条件下会失效，
  发现这个问题，回去补充 fallback 规则。

[维度 6 · 布局]
叙事顺序的理由——为什么这个 section 在前，那个在后，
是情绪先行还是信息先行，漏斗逻辑怎么走。

→ Verification：回头检查叙事节奏，漏斗逻辑是否成立。

[维度 7 · 深度与层级]
z 轴关系，阴影哲学——是写实阴影还是发光高亮，和整体风格的一致性。

[维度 8 · 设计宜忌]
推荐做法来自前面维度推导出的正向决策。
避免做法包含功能边界——为什么某些功能不做，技术边界在哪里。

[维度 9 · 响应式]
```
